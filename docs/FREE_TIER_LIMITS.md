# Free-tier limits and how this project fits

Limits change. Figures below were checked against the providers' own documentation on 22 Nov 2026. Re-check before submitting.

| Service | Role here | Free-tier limit | Our usage |
|---|---|---|---|
| GitHub | Code, data, CI trigger | Per-file limit 100 MB, repos should stay small. Actions are free for public repos. | Whole project is about 3.5 MB. Largest file is `transactions.csv` at 0.7 MB. |
| Streamlit Community Cloud | Hosting the app | Apps are put to sleep after 12 hours without visitors and wake on request. Apps share a resource cap per account (Streamlit's docs describe an over-limit message, not exact numbers, so check the "Manage your app" page). | About 240 MB peak memory in our test, about 1.5 s first render, queries 20 to 150 ms. |
| Supabase (Stage 2) | Hosted Postgres | 500 MB database per project, 5 GB egress, 2 active projects, free projects pause after 1 week of inactivity. | Database is about 3 MB, so under 1% of the 500 MB limit. |
| GitHub Actions | CI | Free minutes for public repos. | Test run takes under a minute. |

## What each limit means in practice

- **Sleeping apps.** The first visitor after 12 idle hours waits for a wake-up. Mitigation: open the app before a demo.
- **Supabase pausing.** Data is kept, but queries fail until the project is restored from the dashboard. Mitigation: the app falls back to SQLite if the `DATABASE_URL` secret is removed.
- **Memory.** Queries aggregate in SQL and only small result sets reach pandas. The one large result is the CSV export (about 15,000 rows). At 50,000+ rows, export should be limited or paginated.
- **Statelessness.** Streamlit's disk is not durable, so the app never writes data. Data changes go through git (SQLite) or the Supabase loader.
- **Cost guardrails.** No paid service is used. Supabase and Streamlit show usage in their dashboards, so check them before the demo.
